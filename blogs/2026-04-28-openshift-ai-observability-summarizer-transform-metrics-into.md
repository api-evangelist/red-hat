<p>Every SRE knows the feeling. You open Grafana, stare at 14 panels of time-series data, and try to answer one deceptively simple question: Is anything wrong?</p><p>Dashboards are excellent at displaying data. They are far less effective at conveying meaning. As Red Hat OpenShift clusters grow with dozens of namespaces, GPU-accelerated AI workloads, and vLLM inference services, the gap between what the metrics say and how you should act widens. Platform teams end up mentally stitching together CPU utilization graphs, pod restart counts, GPU temperatures, and request queue depths. They rely on pattern recognition to catch the anomaly before it escalates into an incident.</p><p>Managing these environments becomes more difficult as they grow. A single Grafana dashboard might surface the right signal for a three-node cluster. At enterprise scale—with varied GPU hardware, multiple inference engines, and dependencies across namespaces—static panels cannot reliably show the most important insights.</p><p>We asked a different question: What if the system could combine that data for you?</p><h2>Architecture: From Prometheus to a large language model</h2><p>The Red Hat OpenShift AI observability summarizer is not a chatbot bolted onto a dashboard. It is a purpose-built pipeline that transforms raw time-series data into actionable, human-readable insights. The design is layered. Each stage reduces noise and increases signal so the large language model (LLM) receives only the data it needs to produce a focused answer.</p><p>The pipeline flows through five distinct layers:</p><ol><li><strong>Intent extraction:</strong> Classifying what the user asks.</li><li><strong>Metric discovery:</strong> Identifying which of the approximately 1,800 metrics are relevant.</li><li><strong>Query generation:</strong> Building type-aware PromQL for each selected metric.</li><li><strong>Statistical analysis:</strong> Applying anomaly detection, trend analysis, and health scoring.</li><li><strong>LLM summarization:</strong> Transforming structured analysis into a natural-language narrative.</li></ol><p>Each layer is deliberate. Each one reduces noise. The following sections walk through them in detail.</p><h3>Intent extraction: Understanding what you are really asking</h3><p>When a user asks, "How are my GPUs doing?," the system does not simply search for metrics containing the word GPU. It classifies the intent behind the question into one of eight recognized types. Each type maps to a different query strategy, as detailed in the following table.</p><div><table><thead><tr><th><strong>Intent</strong></th><th><strong>Example question</strong></th><th><strong>Query strategy</strong></th></tr></thead><tbody><tr><td><code>current_value</code></td><td>"What is the GPU temperature?"</td><td>Instant query</td></tr><tr><td><code>count</code></td><td>"How many pods are running?"</td><td>Aggregated count</td></tr><tr><td><code>average</code></td><td>"What is average CPU usage?"</td><td><code>avg() </code>over time range</td></tr><tr><td><code>percentile</code></td><td>"What is P95 latency?"</td><td><code>histogram_quantile()</code></td></tr><tr><td><code>top_n</code></td><td>"Which pods use the most memory?"</td><td><code>topk()</code></td></tr><tr><td><code>comparison</code></td><td>"Compare latency across models"</td><td>Multi-series query</td></tr><tr><td><code>trend</code></td><td>"How has GPU utilization changed?"</td><td>Range query with slope analysis</td></tr><tr><td><code>rate</code></td><td>"What is token throughput?"</td><td><code>rate()</code> or <code>increase()</code></td></tr></tbody></table></div><p>This classification is important because the same metric requires different PromQL depending on the user intent. A counter like <code>vllm:num_requests_total</code> requires <code>increase()</code> to answer "How many requests arrived in the last hour?" but <code>rate()</code> to answer "What is the current throughput?" Selecting the wrong function produces numbers that are technically valid but not useful for operations. The intent layer prevents these errors at the source.</p><h3>Metric discovery: Signal selection at scale</h3><p>This layer is where the core design work lives. An OpenShift cluster running GPU-accelerated workloads can expose thousands of Prometheus metrics. Most of these metrics are irrelevant to a specific question. Sending every metric to a language model wastes tokens, degrades response quality, and increases the risk of hallucinations. The discovery layer filters data intelligently.</p><h4>Knowledge base: Metrics catalog</h4><p>Approximately 1,800 pre-categorized OpenShift metrics are stored in a bundled JSON file. These are organized into 19 categories, including <strong>Cluster Health</strong>, <strong>Node Hardware</strong>, <strong>Pods &amp; Containers</strong>, <strong>GPU &amp; AI/ML</strong>, <strong>Networking</strong>, and <strong>Storage</strong>. Each metric entry carries three pieces of metadata:</p><ul><li><strong>Priority (high, medium, low):</strong> The system only considers high and medium priorities during discovery to keep the candidate set manageable.</li><li><strong>Semantic keywords:</strong> These are generated through a five-tier relevance system to enable fast matching against user queries.</li><li><strong>Type metadata:</strong> This includes counter, gauge, histogram, or summary types. The query generator uses this metadata to select the correct PromQL pattern.</li></ul><p>The catalog is bundled into the container image at build time. A cold-start lookup completes in approximately 15 milliseconds.</p><h4>Dynamic GPU discovery</h4><p>GPU metrics present a unique challenge: they vary by vendor. NVIDIA exposes <code>DCGM_FI_DEV_GPU_TEMP</code>. Intel Gaudi reports <code>habanalabs_temperature_onchip</code>. AMD uses its own prefix conventions. Hardcoding these names is difficult to maintain.</p><p>Instead, the system queries Prometheus at startup for metrics that match configurable vendor prefixes. It detects the primary GPU vendor present in the cluster and merges discovered GPU metrics into the catalog with the appropriate priority levels. This discovery process runs asynchronously. It completes in about one to two seconds and does not block the server from accepting requests.</p><p>To prepare for new metric naming conventions, platform teams can supply additional prefixes via environment variables: <code>GPU_METRICS_PREFIX_NVIDIA</code>, <code>GPU_METRICS_PREFIX_INTEL</code>, and <code>GPU_METRICS_PREFIX_AMD</code>. These variables are additive. Custom prefixes extend the built-in defaults instead of replacing them. This means you can support new GPU monitoring exporters without a code change or image rebuild.</p><h3>Catalog validation</h3><p>A bundled catalog can become outdated as clusters evolve. A <code>CatalogValidator</code> runs at startup to check catalog entries against the live Prometheus instance. It removes metrics that no longer exist and adds new ones at medium priority. Validation completes within a 10-second timeout and does not block server readiness.</p><h3>Runtime catalog (after startup)</h3><p>The static catalog is only the baseline. After validation, the service holds a single, cluster-specific catalog. Outdated names from the bundle are removed, and new Prometheus names that match the category structure are added. GPU and vLLM metrics are included in the working set for the chat. The semantic scoring described in the next section runs against this merged catalog.</p><h3>Semantic scoring</h3><p>When a user asks a question, the system ranks candidate metrics using a relevance scoring system. Each metric is scored across four dimensions:</p><ul><li>Keyword pattern matching against user intent</li><li>Metric type relevance</li><li>Name specificity</li><li>Catalog priority</li></ul><p>Domain-specific bonuses sharpen the ranking. GPU and vLLM metrics receive a 15-point boost when the question involves those domains. Common abbreviations like TTFT, TPOT, and ITL receive a 20-point boost to help the correct latency metric appear first. This scoring ensures the system selects the most relevant metric for operations instead of just the most common one.</p><h2>Query generation: Metric type awareness</h2><p>Correct PromQL generation is more complex than it appears. Prometheus defines four metric types, and each requires a different query pattern. Applying the wrong function to a metric produces results that look correct but are not useful for operations. This is a common error in hand-built dashboards.</p><ul><li><strong>Counters</strong> (requests, errors, tokens processed): These always require <code>rate()</code> or <code>increase()</code>. Querying a counter's raw value returns a number that only increases, which does not show recent behavior.</li><li><strong>Gauges</strong> (temperature, queue depth, memory usage): These display current or averaged values directly. Applying <code>rate()</code> to a gauge produces nonsensical derivatives.</li><li><strong>Histograms</strong> (latency distributions): These require <code>histogram_quantile()</code> to extract meaningful percentiles. Raw bucket values are unintelligible to most operators.</li><li><strong>Summaries </strong>(pre-calculated averages): Require dividing <code>rate(sum)</code> by <code>rate(count)</code> to produce correct averages over a time window.</li></ul><p>The system maintains a type registry that maps each discovered metric to its Prometheus type and automatically selects the correct query pattern. This prevents errors that lead to incorrect data.</p><h3>Smart fallbacks</h3><p>Not every metric is available on every cluster. The system uses fallback chains to ensure the user receives a useful response instead of an empty result. For example, when querying total request counts:</p><ul><li>1st: <code>vllm:num_requests_total</code> (preferred)</li><li>2nd: <code>vllm:request_success_total</code> + <code>vllm:request_errors_total</code> (computed sum)</li><li>3rd: <code>vllm:request_success_total</code> (lower bound)</li></ul><p>This approach ensures operators always receive the best available answer, even if the cluster metrics differ from the expected baseline.</p><h3>From numbers to context</h3><p>Before the LLM call, the pipeline compresses time series into structured inputs. This includes numeric summaries, optional correlated logs and traces, and a distinction between computed facts and model conclusions. This reduces token use and ensures the system relies on data rather than hidden logic.</p><h3>Per-metric summaries</h3><p>For each metric, the system computes basic aggregates over the user query window, such as the average and latest values. This allows the model to see the data range without processing every raw sample. This reduces noise and cost while remaining accurate to the underlying data.</p><h3>Severity and change: LLM interpretation</h3><p>We do not currently use separate services to create labels like <strong>spike</strong>, <strong>dip</strong>, or <strong>trend</strong>. We also do not use a health score based on manual thresholds. The current implementation provides fixed baseline labels, such as <strong>stable trend</strong> and <strong>normal severity</strong>, alongside the numeric summaries.&nbsp;</p><p>The model uses these as a starting point. It can override them based on the data. For example, it might note a sharp increase even if the label is <strong>stable</strong>. Replacing these placeholders with computed classifiers is a natural next step. The pipeline's job is to supply accurate aggregates and baseline context; the model's job is to interpret them.</p><h3>Correlated logs and traces</h3><p>When you enable correlation, the system attaches related log lines and trace spans to the metric data. This helps the system link symptoms across different signals, such as connecting latency to errors or resource pressure elsewhere, instead of treating each series in isolation.</p><h3>Why this layer stays intentionally thin</h3><p>The design prioritizes honest signal engineering: providing specific, accurate data to the LLM. Richer statistical classifiers or scored health models can be added over time. Currently, the product provides clear data aggregation. This maintains a distinction between computed numbers and the model's interpretation, so readers and operators understand what is automated versus inferred.</p><p>As shown in Figure 1, the system identifies latency spikes by querying specific percentiles, providing the model with a clear trend rather than just a single data point.</p><figure class="rhd-u-has-filter-caption">

It has also queried the data with type-aware PromQL and added annotations for trends, anomalies, and health scores. The LLM task is deliberately narrow and well-defined: transform structured analysis into clear, natural-language narrative.</p><p>The system supports multiple LLM providers, including Anthropic Claude, OpenAI GPT, Google Gemini, and locally hosted Llama models using Llama Stack. We set the temperature to 0 for deterministic, reproducible results. The response is not a generic summary; it is a focused answer to the user question based on actual metric values.</p><p>The system provides a summary of vLLM metrics with recommendations, as shown in Figure 4.</p><figure class="rhd-u-has-filter-caption">

<h2>Scope control: Cluster-wide versus namespace</h2><p>Aggregation scope is a key architectural decision for this pipeline. The level of aggregation affects signal clarity and LLM response quality.</p><p>Cluster-wide queries use aggregation functions, such as <code>avg()</code>, <code>max()</code>, <code>sum()</code>, to combine per-pod, per-node, and per-GPU metrics into fleet-level summaries. This prevents the model from processing hundreds of individual time-series, which reduces noise.</p><p>Namespace-scoped queries add a <code>{namespace="X"}</code> label filter. This produces precise, targeted results when a user needs to investigate a specific workload or service.</p><p>The system defaults to cluster-wide to provide an overview. Users can then drill into specific namespaces for more detail. This mirrors the standard troubleshooting workflow of most SREs: start broad, then narrow.</p><h2>The console plug-in: Access insights within your workflow</h2><p>The summarizer runs as an OpenShift console plug-in. <h2>Why summarization outperforms dashboards</h2><p>Summarization offers several improvements over traditional dashboard-based monitoring.</p><h3>Dashboards are passive</h3><p>They present data and wait for a human to interpret it. The summarizer is active. It interprets the data, identifies important information, and presents a conclusion. For routine health checks, this reduces a 10-minute investigation into a 10-second read.</p><h3>Dashboards are static</h3><p>A Grafana panel shows the same visualization whether metrics are normal or alarming. The summarizer adapts its response to the data. If the system is healthy, the tool provides a brief update. If there are issues, it explains them and recommends actions.</p><h3>Dashboards require expertise to read</h3><p>Interpreting a histogram heatmap or a multi-series rate graph requires training and experience. Natural-language summaries are accessible to anyone on the team, from junior engineers to incident commanders to product managers checking on SLA compliance.</p><h3>Dashboards do not correlate signals</h3><p>Each panel exists in isolation. Recognizing that a CPU spike, a pod restart loop, and a latency increase are all symptoms of the same underlying issue requires a human to draw those connections. The summarizer connects these signals automatically through metric correlation and contextual analysis.</p><h2>Prompt engineering: Structure, signal, and noise reduction</h2><p>The quality of the LLM response depends on the quality of its input. The system prompt is not a simple instruction string, but a structured document designed to reduce errors, maximize relevance, and produce consistent output across model providers.</p><h3>Signal selection</h3><p>The prompt receives only the metrics that survived the discovery and scoring pipeline. This is typically three to five data points. Each metric includes its current value, trend classification, anomaly status, and unit of measurement. This prevents the model from inventing data or making assumptions about missing metrics.</p><h3>Structured context</h3><p>Statistical analysis results, such as health scores, anomaly flags, trend directions, are passed as structured fields rather than text. This provides the model with specific facts and reduces the risk of misinterpretation or embellishment.</p><h3>Noise reduction</h3><p>The system summarizes or omits metrics that are stable and within normal ranges. The prompt instructions direct the model to focus on actionable findings, such as anomalies and trends. This is more effective than listing every value. The result is a response that reads like an SRE incident summary instead of a data dump.<strong>&nbsp;</strong></p><h2>Try it yourself</h2><p>The <a href="https://github.com/rh-ai-quickstart/openshift-ai-observability-summarizer">AI observability summarizer</a> is open source and designed for Red Hat OpenShift and Red Hat OpenShift AI environments.</p><p>Use the following command to install the summarizer in your cluster:</p><pre><code class="language-plaintext">make install NAMESPACE=your-namespace</code></pre><p>After installation, open the OpenShift web console and navigate to <strong>Observe</strong> → <strong>AI Observability</strong> in the sidebar.</p><p>We welcome contributions from the community.</p><h2>The takeaway</h2><p>A common misconception about AI-powered observability is that the language model is the most difficult part. It is not. The LLM is the final 10% of the work. It translates structured analysis into language. The other 90% is signal engineering: this is the process of ensuring the model receives clean, relevant, and correctly computed data.</p><p>That work breaks down into four capabilities:</p><ul><li><strong>Knowing which metrics matter:</strong> This involves catalog management, dynamic discovery, and semantic scoring.</li><li><strong>Querying them correctly:</strong> This uses type-aware PromQL generation with smart fallbacks.</li><li><strong>Reducing noise statistically:</strong> This involves anomaly detection, trend analysis, and health scoring.</li><li><strong>Controlling scope:</strong> This uses cluster-wide aggregation and namespace-level filtering.</li></ul><p>When you get these four things right, the LLM can do what it does best: turning numbers into narrative.</p><p>Dashboards show you data. This system tells you what it means.</p>
